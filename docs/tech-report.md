## 1. 项目概述

### 1.1 背景与痛点

2 型糖尿病患者的日常管理中，饮食是控糖的核心环节，但现实中存在三类痛点：① 吃之前不知道这顿饭碳水化合物和升糖负荷大概多少；② 网上营养建议汗牛充栋，真假难辨、无法对应到自己的餐盘；③ 即使知道「要少吃升糖快的」，也缺少可执行、可核验的个性化建议。

### 1.2 产品定位

Glucoguard 是一个面向慢病控糖人群的 **AI Native 饮食助手**：拍一张餐盘照片 → 识别食物与份量 → 算碳水/升糖负荷 → 检索权威指南与联网资料 → 经过安全护栏 → 输出连贯成文、逐句带引用编号的饮食建议。**每一句结论都可以点回证据原文**（本地指南摘编 / 联网页面 / 食物数据库 / 个人餐食记录），检索与工具调用全程可在「执行过程」卡片中回放。

合规边界（产品设计硬约束）：定位为饮食与生活方式参考，**不是医疗器械**——不做诊断、不给胰岛素/降糖药剂量建议，也不回答控糖饮食以外的问题（物理推导、翻译、天气、代码等，即使联网搜到也拒答）。

### 1.3 一句话能力

拍照识餐、语音提问、多智能体检索问答、证据可回放、健康档案与趋势报告、饮食日记本、账号体系与多用户数据隔离。

## 2. 需求分析

### 2.1 用户画像

- 主要用户：2 型糖尿病患者及其家属，年龄层 35–65 岁，习惯用手机拍照记录三餐；
- 典型场景：饭前拍一张餐盘照片问「这顿适合我吃吗」；饭后问「上一餐吃了什么 / 血糖怎么样」；购物时问「燕麦和白米饭哪个升糖慢」。

### 2.2 功能需求

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 拍照识餐 | 上传餐图 → VLM 返回食物名/份量区间/置信度，逐项可修正；图片落盘后可按 `image_id` 回放 |
| F2 | 语音输入 | 浏览器 Web Speech API（zh-CN）把口述转成问题追加到输入框；不支持时置灰提示，不影响打字 |
| F3 | 带引用的智能问答 | 多智能体检索问答，正文中 `[E#]` 可点击，右侧证据面板展示原文、来源、段落定位 |
| F4 | 执行过程可视化 | SSE 实时推送节点事件；运行态 HUD（当前角色、进度段、耗时）+ 完整轨迹回放；历史任务可随时回放 |
| F5 | 健康档案与趋势 | 身高体重年龄活动量 → BMI；餐食记录 + 血糖读数；近 7 天碳水柱状、近 14 天血糖折线、AGP 风格分区报告 |
| F6 | 饮食日记本 | 餐食记录以「一本日记」形态呈现：右侧图钉迷你卡，点击展开大日记本；一页一天、可翻页、可编辑/补血糖/删除；手写体 + 荧光笔高亮 |
| F7 | 个人记忆问答 | 提问涉及「上一餐/我之前吃过…」时，个人餐食记录作为 `memory` 证据通道入池并被引用 |
| F8 | 账号与多用户隔离 | 用户名+密码注册登录；餐食/血糖/运行历史/会话记忆按 `user_id` 隔离；不登录则归单机演示身份 `local` |

### 2.3 非功能需求

| 类别 | 要求 | 实现 |
|---|---|---|
| 安全合规 | 主题护栏 + 提示词注入拦截；拒答无源结论；医疗免责 | `adapters/guard/` + `core/services/injection.py` + 置信度阈值拒答 |
| 隐私 | 密码 scrypt 哈希+随机盐；令牌只存 SHA-256，30 天有效；SQL 归属条件隔离；密钥只走环境变量不入库 | `core/services/accounts.py`、`app/api/deps.py` |
| 可观测 | SSE 节点事件、每节点耗时、MCP 调用审计 JSONL、任务快照持久化 | `core/observability`、`adapters/tools/governance.py`、SQLite `runs` 表 |
| 可用性 | 后端挂掉前端显式提示「后端未连接」；R2R/联网/工具单点故障降级兜底，不炸主流程 | `deploy/drill_degrade.sh` 演练 3/3 通过 |
| 性能 | 流式首字延迟、检索超时（8s）、工具超时（10s）、联网超时（3s）+ 短时缓存与失败冷却 | `infra/config.py`、`adapters/retrieval/web.py` |

### 2.4 差异化

与普通「营养查询小工具」的本质区别：不是把知识罗列给用户挑，而是**每一条结论都能点回证据原文核验**，「无源不答」宁可拒答也不编造——这对医疗健康场景的信任建立是关键。

## 3. 系统架构设计

### 3.1 总览

```
浏览器端（React 19 + TypeScript + Vite + Astryx 设计系统）
  │  SSE（/api/chat 流式事件）+ REST（auth/meals/food/tasks）
  ▼
FastAPI（app/main.py）
  │  装配：guard / retriever / llm / tools / stores
  ▼
LangGraph 多智能体图（core/graph）：planner → retriever → executor ┐
                                        analyst ⇄ critic → writer ┘
  │
  ├─ adapters/llm        LiteLLM 双档路由（fast/strong）+ FakeLLM（离线）
  ├─ adapters/retrieval  R2R 混合检索 / 联网搜索(博查|Tavily|DDGS) / 云盘 / fake
  ├─ adapters/tools      MCP stdio server（10 个控糖工具）+ 治理层（审计/超时/参数校验）
  ├─ adapters/vision     VLM 拍照识餐
  └─ adapters/guard      主题 + 注入安全护栏
  ▼
数据层：SQLite（runs.db：users/sessions/runs/meal_logs/glucose_readings）
        PostgreSQL + pgvector（R2R 知识库，8 篇指南摘编 37 段）
        本地文件（上传餐图、工具审计 JSONL）
```

### 3.2 后端分层

- `app/`：FastAPI 入口与路由（auth / chat / food / meals / tasks），身份解析在 `app/api/deps.py`（令牌即身份，请求体里的 user_id 一律忽略）；

- `adapters/`：只做协议翻译——LLM 路由、R2R/联网检索、VLM、MCP 工具、护栏、可观测；
- 装配集中在 `app/main.py`。

### 3.3 前端结构

React 19 + TypeScript（strict）+ Vite + Astryx 设计系统（主题 token、深浅色自动跟随）。状态管理为三个 Context Store（`auth` / `runs` / `ui`），SSE 流式状态机集中在 `runs`。页面：控糖工作台（`ChatPage`）+ 浮动健康档案卡（`HealthFileCard` 内嵌 `ProfilePage`）+ 饮食日记本书（`MealDiaryBook`，右侧图钉迷你卡展开）。组件化：证据面板、执行过程 HUD、餐食卡、图表（自绘 SVG）、登录/记录弹窗、语音按钮等 15+ 组件。

### 3.4 部署架构

`deploy/docker-compose.yml` 起检索栈：postgres（pgvector） + infinity（本地中文 embedding：BAAI/bge-small-zh-v1.5，端口 7997） + R2R 3.6.6（宿主机 7272）；后端 `uvicorn app.main:app`（8000）；前端 `vite build` 后静态托管或 dev 代理（5173→8000）。`deploy/up.sh` 一键串联，`--offline` 走 fake 模式全离线演示。

## 4. AI 技术方案（重点章节）

### 4.1 技术选型理由

| 技术点 | 选型 | 理由 |
|---|---|---|
| 编排框架 | LangGraph 多智能体图 | 饮食问答需要「规划→检索→工具→分析→审校→成文」分工与打回闭环，单次 RAG 调用无法表达；图的轮数预算天然可控 |
| 大模型接入 | LiteLLM 统一路由 + 双档分工 | 一个入口对接多家模型（deepseek 等），便于替换；fast 档（默认关闭思考模式）跑规划/结构化抽取/成文/置信度评分，strong 档跑分析——兼顾延迟、成本与质量 |
| 知识检索 | R2R 混合检索（向量 + BM25，RRF 融合，服务端精排） | 单纯向量召回在中文医疗短段上不稳，混合检索 + 精排实测 Recall@5 = 0.9737 |
| 工具协议 | **MCP（Model Context Protocol）stdio server** | 工具与模型解耦的开放协议：10 个控糖工具以标准 MCP 暴露，外挂治理层（审计/超时/参数镜像校验）后可整体替换实现，fake 模式离线对齐同一契约 |
| 端侧 AI | 浏览器 Web Speech API（语音输入） | 识别在本机完成，不上传云端，降低延迟与隐私风险 |
| 数据与记忆 | SQLite 业务库 + 结构化记录转证据 |餐食/血糖是强结构化小数据，SQLite 零运维够用；个人记录经召回后作为 `memory` 通道证据参与引用 |

### 4.2 集成方式

- **MCP 工具层**：`adapters/tools/mcp_server.py` 以 stdio 子进程启动，`mcp_client.py` 作为 ToolGateway 挂进 LangGraph；10 个工具：食物成分查询、单项 GL、整餐 GL 合计、个人血糖统计（均值/SD/CV/LAGE/区间读数占比）、每日碳水目标与三餐分配、通用增减/求和/均值。**工具入参由后端从餐食、档案，读数里取，模型不填数**，避免幻觉参数；`governance.py` 做调用审计（JSONL）、单次超时（10s）、入参按 schema 镜像校验，超时返回 `ok:false` 不炸图。
- **证据与引用**：各检索通道（local/web/cloud/image/tool/memory）汇入统一证据池，编号 `E1…En`；正文中 `[E#]` 可点击，前端右侧面板按「文件预览」方式展示原文（行号、来源文件、段落/页码/时间码定位、外链可打开）。引用进 prompt 前经 `injection.py` 中和指令型片段，引用卡片仍展示原文。
- **流式可观测**：`/api/chat` 以 SSE 推送 `run → guard → node* → deliverable → done`；前端执行卡实时显示当前角色、步骤进度段、已用/总耗时，结束后可回放完整轨迹；任务快照持久化到 SQLite，历史可回放。
- **安全护栏**：输入侧 guard 拦截主题外问题与注入（实测 39/39 拦截、0/11 误拦、单次 0.01ms）；输出侧置信度低于阈值（0.45）拒答——"无源不答"。
- **置信度双通道**：LLM 评分（fast 档结构化输出）为主，失败时回退确定性公式（支撑率 0.5 + 支撑强度 0.3 + 引文广度 0.2），并标注 `confidence_source`，不静默冒充模型评分。

### 4.3 优化策略

- **检索优化**：联网结果短时缓存 + 失败 20s 冷却，避免反复重试拖慢回答；官方/学会域名加权；单通道超时不拖垮整体（线程池扇出 + 总超时）；R2R 侧开启 `use_hybrid_search`。
- **成本与延迟**：fast 档默认 `{"thinking":{"type":"disabled"}}` 关闭思考模式（实测与换模型同耗时）；编排预算：审校打回轮数上限、分析员断言上限 7 条，轮数用尽在 Writer 前挂起等人工放行（前端「一键放行」）。
- **质量保障**：成文智能体把审校通过的断言连成 2–4 段口语化回答，引用编号一个不多一个不少、硬数字照抄、长度受约束，任一项不过或调用失败就退回逐条断言并把原因写进轨迹。
- **降级与兜底**：`MRAG_MODE=fake` 全离线可演示（FakeLLM/FakeRetriever/FakeTools 与在线共用同一套工具算法和同一批知识卡）；`deploy/drill_degrade.sh` 演练掐 R2R / 错 key / 工具超时三类故障，均输出 degraded 兜底结论（3/3）。
- **实测指标**（`docs/metrics.md`，本机可复现）：

| 指标 | 实测 |
|---|---|
| 后端测试 | **389 passed**（全离线 pytest） |
| Recall@5 / MRR（金标 50 条，去掉库外与纯工具题后 n=38） | **0.9737 / 0.9257** |
| 关键来源命中率 / 引用可解析率 | **1.00 / 1.00** |
| 无源断言率 / 成文率（pipeline n=23） | **0.00 / 1.00** |
| 答案分（LLM-as-judge） | **1.00** |
| 注入拦截率 / 良性误拦率 | **39/39 / 0/11** |
| 降级演练 | **3/3** |
| 直连大模型 vs RAG 答案分（消融） | 0.725 vs **1.00** |

### 4.4 端云协同（当前与规划）

- 当前端侧：Web Speech API 语音识别（本机完成）；前端本地完成 BMI 计算、图表绘制、日记分页等。
- 规划中：把「是否在问个人历史」这类轻量意图分类下沉到浏览器端小模型（ONNX Runtime Web + WebGPU，Web Worker 内运行，失败回退云端 fast 档），进一步降低延迟与成本——属端云协同架构的下一步。

## 5. 核心功能实现

### 5.1 拍照识餐（F1）

上传餐图 → VLM 返回食物名/份量区间/置信度 → 用户可逐项修正 → 落盘后获得 `image_id`，可经 `GET /api/food/images/{image_id}` 回放。识别结果可一键「记下来」进入饮食日记，并作为 `image` 通道证据。

### 5.2 带引用的智能问答（F3）

正文 `[E#]` 为可点击 chip；点击后右侧滑出证据面板（来源文件/网页、通道徽标、段落或页码定位、原文逐行展示），再次点击收起。拒答/降级时有显式横幅说明原因，置信度与引用统计压在回答末尾。

【图 5-1】问答 + 证据面板截图

### 5.3 执行过程可视化（F4）

运行时右下角执行卡自动聚焦：旋转扫描动画、当前角色中英文名、步骤编号、节点耗时与总耗时、六段进度条；完成后展示完整轨迹（每步耗时与文字反馈）。历史会话可回放旧任务快照。

### 5.4 健康档案与趋势（F5）

左下角档案图标打开浮动档案卡：基础信息（身高/体重/年龄/活动量，本地计算 BMI 与分级）+ 健康趋势。趋势报告参照 AGP 口径但明确按「读数占比」统计：概览指标卡（平均血糖、达标占比 TIR、CV、极差）、读数分布、单日 24 小时 / 区间血糖曲线（目标区间阴影带）、按小时叠加、餐后时段、碳水×血糖散点、每日碳水柱状，支持范围切换与 CSV 导出。只画已记录数据，不补点不预测。

【图 5-2】健康趋势报告截图

### 5.5 饮食日记本（F6）

餐食记录以「一本日记」呈现：页面右侧一张图钉钉住的迷你卡片（红图钉 + 暖纸横线 + 手写体，显示最近一天日期与最新一餐摘要），点击从右侧展开大日记本——螺旋装订左侧、顶部和纸胶带、横线纸背景、霞鹜文楷手写体正文；一页一天（大日期 + 当天餐数/碳水合计/血糖最高最低），餐次为荧光笔高亮块，照片为拍立得样式，血糖为读数 chip；底部按天翻页。日记内可直接「记一顿 / 编辑 / 补血糖 / 删除」（删除走红色 AlertDialog 二次确认）。

【图 5-3】日记本书展开态截图

### 5.6 个人记忆证据通道（F7）

问答入口先判断是否在问个人历史：规则正则 cue（上一餐/上一顿/前一顿/上次/之前/…）为第一道，未命中时用 fast 档模型做结构化意图分类（`HistoryIntent`），失败回退纯规则。命中后从该用户餐食记录中取最近若干条转成 `memory` 证据（含时间、食物克数、碳水是否为食物库估算、餐前/餐后血糖、备注），与指南、联网结果一起入池被引用；空档案时给出「还没有任何餐食记录」的占位证据，避免整轮无引用拒答。

### 5.7 账号体系与多用户隔离（F8）

注册登录开箱可用：用户名 3–24 位、密码 8–128 位；密码存 `scrypt$16384$8$1$盐$派生值`（标准库 `hashlib.scrypt` + 16 字节随机盐，`hmac.compare_digest` 比对，用户名不存在时也跑一次哈希防时序枚举）；令牌 `secrets.token_urlsafe(32)`，库里只存 SHA-256，有效期 30 天；同一用户名连错 5 次冷却 300s。令牌即身份，归属条件写进 SQL（`WHERE … AND user_id=?`），跨用户读改删当不存在；隔离范围覆盖餐食、血糖、运行快照与历史、断点放行、会话记忆。不登录归单机演示身份 `local`。令牌只存浏览器 localStorage。

### 5.8 安全护栏与拒答（F3/F8 的保障）

输入侧拦截主题外问题（胰岛素剂量、诊断、与控糖无关的闲聊/代码/天气等）与提示词注入；输出侧置信度低于 0.45 拒答并给出原因。前端对拒答/降级/拦截/断点四类状态都有显式横幅与操作入口。

## 7. 创新点说明

### 7.1 技术创新点

1. **证据可回放的引用体系**：`[E#]` 一键点开原文面板（行号/段落/页码定位、来源与通道徽标），引用可解析率实测 1.00；提示词注入中和与引用原文分离展示；
2. **成文智能体 + 审校打回 + 人工断点闭环**：断言经审校（只拦硬错误）后由成文智能体连缀成口语化回答，引用编号/硬数字/长度受约束，失败回退逐条断言；轮数用尽挂起等人工放行；
3. **MCP 标准协议 + 治理层**：10 个控糖工具走标准 MCP stdio，外挂审计 JSONL / 超时熔断 / 参数镜像校验，工具入参由后端注入、模型不填数；
4. **置信度双通道与无源拒答**：LLM 评分 + 确定性公式兜底，低于阈值拒答并给原因，无源断言率 0.00；
5. **个人记忆双保险召回**：结构化餐食记录转证据通道，正则 cue + 端上触发、云端 fast 模型意图分类兜底；
6. **端侧原生 AI + 手账式承载**：Web Speech 本机语音；日记本用手写字体/荧光笔/图钉等手账语言承载 AI 产出的健康记录。

### 7.2 应用创新点

1. **拍照→碳水/GL→指南→带引用建议的完整闭环**，食物碳水来自《中国食物成分表》并逐项标来源，查不到权威 GI 的只报碳水不估算 GL；
2. **饮食日记本书**：把健康记录从冷冰冰的列表做成可翻阅、可编辑的日记（图钉迷你卡入口，一页一天，手写排版）；
3. **AGP 风格个人血糖趋势报告**（达标区间阴影带、读数分布、餐后时段、碳水×血糖散点），回答内再按问题自动附个人数据图；
4. **多用户隔离开箱即用**：注册登录即可用，不登录也有单机演示身份，数据按 `user_id` 严格隔离；
5. **全链路可观测**：从提问到每一步智能体动作、工具调用审计，都可在界面回放。

## 8. 总结与展望

### 8.1 已完成

多智能体检索问答闭环、MCP 工具层与治理、证据可回放引用、安全护栏与置信度拒答、拍照识餐、语音输入、健康档案与趋势报告、饮食日记本、账号体系与多用户隔离；389 离线测试 + 金标/护栏/降级评测全部通过。

2. 接入 CGM 设备数据，补全动态血糖报告；
3. 增加请求级限流与配额、更多食物库条目与指南；
